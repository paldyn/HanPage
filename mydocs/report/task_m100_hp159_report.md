# Task #159 (M100) — Windows 혼합 배율 모니터의 새 창 위치 최종 보고서

Issue: #159 · 계획: [task_m100_hp159.md](../plans/task_m100_hp159.md)

## 1. 결과 요약

Windows 에서 배율이 서로 다른 모니터를 함께 쓸 때 새 문서 창이 앞 창의 모니터가 아닌 곳에 걸쳐 열리던 문제를 고쳤다.
새 창 위치를 플랫폼의 전역 좌표계(macOS point, Windows 물리 픽셀)로 계산하고, Windows 에서는 새 창을 처음부터 그 자리의
모니터에서 만든다. 그 자리의 논리 좌표가 그 모니터만 가리키면 지금처럼 바로 만들고, 먼저 나열된 다른 모니터를 가리킬 때만 그
모니터 안의 다른 자리에 숨겨 만든 뒤 같은 모니터 안에서 옮긴다. macOS 동작은 바꾸지 않았다.

## 2. 변경 내역

| 위치(`HanPage-Desktop/src-tauri/src/lib.rs`) | 내용 |
|---|---|
| `Space` | 좌표계 선택(`current()` = Windows 물리 / 그 밖 논리), 물리 좌표 → 좌표계(`point`), 논리 길이 → 좌표계(`length`) |
| `cascade_position` · `plan_cascade` | Tauri 에서 창들의 물리 위치·배율과 기준 창 모니터의 작업 영역(물리)·배율을 읽고(`cascade_position`), 좌표계로 바꿔 간격(28 논리 px)·창 크기를 기준 창 화면의 배율로 맞춘 뒤 자리를 정한다(`plan_cascade`) |
| `next_cascade_position` | 간격을 인자로 받고 같은 자리 허용 오차를 간격에 비례(논리 4px)하게 |
| `Display` · `displays` · `tao_creation_display` | 모니터 목록(`available_monitors()`, tao 와 같은 나열 순서)과 tao 0.35.3 의 창 생성 모니터 규칙(나열 순서대로 '논리 × 배율' 이 드는 첫 모니터, 왼쪽 경계 여유 포함) |
| `windows_placement` | 대상 모니터를 정하고 바로 만들기(`Direct`) 또는 대상 모니터 안의 다른 자리에서 만든 뒤 옮기기(`Moved`) |
| `build_document_window` | macOS 는 창 설정 x/y. Windows 는 `Direct` 면 창 설정 x/y, `Moved` 면 `visible=false` 로 만든 뒤 `set_position(PhysicalPosition)`·`show()`·`set_focus()` |
| `HanPage-Desktop/README.md` | 알려진 한계에서 이 문제를 지우고 동작 설명에 반영 |

`#[cfg]` 블록 대신 `cfg!(windows)` 로 고르므로 Windows 경로 코드도 macOS 빌드에서 타입 검사를 받는다.

### 3.4 독립 검토

첫 구현(위치 없이 숨겨 만든 뒤 물리 좌표로 옮기기)을 좌표 계산, Windows 실행 동작, 테스트 타당성 관점에서 독립 검토하고
발견마다 검증자 3명이 반박을 시도했다. 확인된 결함과 반영:

| 지적 | 반영 |
|---|---|
| 위치 없이 만든 창은 tao 가 주 모니터 배율로 크기를 정하고, 옮길 때 크기를 다시 정하지 않는다. 주 모니터 배율이 약 1.75배 이상 높고 앞 창이 그 왼쪽·위의 낮은 배율 모니터에 있으면 창이 두 배 크기로 두 모니터에 걸쳐 열린다(창이 주로 걸친 모니터가 그대로라 배율 변경 알림도 없다). 이전 구현은 이 배치에서 정상이었다(회귀) | 처음부터 대상 모니터에서 만든다. 논리 좌표가 대상 모니터만 가리키면 바로 만들고(이 배치), 겹칠 때만 대상 모니터 안에서 만든 뒤 같은 모니터 안에서 옮긴다 |
| Windows 10 에서 '끄는 동안 창 내용 표시' 를 끄면 tao 가 배율 변경 때 크기를 다시 맞추지 않아, 다른 배율의 모니터로 옮긴 새 창이 잘못된 크기로 열린다 | 위와 같다 — 새 창이 배율이 다른 모니터로 옮겨지지 않는다 |
| 혼합 배율 테스트가 넘침·되돌림을 실행하지 않고, '모니터 안' 단언이 앞 단언으로 이미 정해지는 항진식이었다 | 넘침 되돌림 단언을 더하고, 만드는 자리를 tao 규칙과 모니터 영역으로 검사 |

반박된 지적: 혼합 배율 테스트가 Windows 배선과 무관하다는 주장(0/3 — `plan_cascade` 는 `cascade_position` 이 실제로 쓰는 계산이다).

## 4. 미검증·한계

- Windows 혼합 배율 실기: 이 환경은 macOS 라 실제 모니터 배치는 확인하지 못했다. 작업지시자 환경에서 보조 모니터의 앞 창을
  기준으로 새 창 위치(최대화된 앞 창, 오른쪽 아래가 넘쳐 되돌아가는 경우, 주 모니터 왼쪽·위의 낮은 배율 모니터 포함)를 확인한다.
- `Space::current()`·`displays()` 가 실제 값을 읽는지, 숨겨 만든 창을 옮겨 보이는 순서는 단위 테스트로 확인할 수 없다(Tauri
  런타임 필요). Windows 컴파일·Clippy·테스트는 `Desktop check`(#158), 번들은 `desktop-release` 로 확인한다.
- 모니터 목록을 읽은 뒤 창을 만들기 전에 모니터 구성이 바뀌면 판단이 어긋날 수 있다(드묾).
- 대상 모니터가 창보다 작아 창이 모니터 밖으로 걸치는 경우에는 옮긴 뒤 배율이 바뀔 수 있다.
