# Task #156 (M100) — Desktop 문서마다 창 하나 최종 보고서

Issue: #156 · 계획: [task_m100_hp156.md](../plans/task_m100_hp156.md) · base `2b23c21c7` · 코드 커밋 `b608f5508`(1차) + `c83f4e369`(1차 검토 반영) + `98bbfa766`(2차 검토 반영)

## 1. 결과 요약

다른 한글 파일을 열면 새 창에서 연다. 지금 창(가장 최근에 포커스한 창)이 손대지 않은 빈 창이면 그 창에서 열고,
이미 어떤 창에 열렸거나 열리는 중인 파일이면 그 창을 앞으로 가져온다. Finder·탐색기 더블클릭과 연결 프로그램, macOS 최근
문서, 파일 > 열기, 끌어다 놓기가 같은 규칙을 따른다. 파일 > 새 문서·AI 도우미·문서 비교·자동 저장 복구는 지금 창에서 바꾼다.

창이 여럿이 되면서 함께 필요한 동작도 넣었다: 저장하지 않은 창을 닫거나 Cmd+Q 로 끝낼 때 저장 확인, macOS 메뉴
명령은 가장 최근 창에만, 업데이트 적용 전 다른 창 확인, 업데이트 준비 알림은 앱 전체에서 한 번, 창 제목은 문서 이름,
새 창은 가장 최근 창에서 비스듬히 빈 자리에, 자동 저장 복구 제안과 창 크기·위치 기억은 첫 창만.

수정하지 않고 한계로 남긴 지적: 자동 저장 초안은 창을 구분하지 않는 저장소 하나를 쓰므로, 첫 창이 다시 시작하며
복구를 제안할 때 다른 창의 초안과 구분하지 않는다. 두 번째 이후 창이 비정상 종료돼 다시 불러와도 그 창에서는 복구를
제안하지 않는다. macOS Dock 종료·로그아웃과 Windows 로그오프는 창에 묻지 않는다. 설정은 마지막으로 바꾼 창의 값이 남는다.

## 4. 미검증·한계

- Windows 실기(WebView2): 창 생성 스레드, 닫기·Alt+F4, 단일 인스턴스 두 번째 실행(시작 중 경합 포함)의 창 선택.
  데스크톱 번들은 PR CI 에 없으므로 `desktop-release` workflow_dispatch 로 컴파일·번들만 확인한다.
- Windows 혼합 배율 다중 모니터: 앞 창이 배율이 다른 보조 모니터에 있으면 새 창이 다른 모니터에 걸쳐 열릴 수 있다(논리 좌표가
  여러 모니터에 해당하면 tao 가 먼저 나열된 모니터를 고름). 고치려면 Windows 에서 숨긴 창을 물리 좌표로 옮긴 뒤 보여야 해
  실기 확인이 필요하다. 후속 과제로 남긴다.
- 데스크톱 크레이트 단위 검사(35)는 PR CI 에 없다(루트 workspace 밖). 로컬 실행 결과다. CI 에 넣는 작업은 후속 과제다.
- 실제 레지스트리와 실제 브리지를 함께 돌리는 통합 시험이 없다. 2차에서 확인된 결함 대부분이 두 계층의 호출 순서 문제였고,
  검증자들은 scratch 하네스로 확인했다.
- macOS 실기의 닫기 확인·Cmd+Q·응답 없는 창 네이티브 확인·Cmd+Q 창 상태 저장: 이 환경에 보조 접근 권한이 없어 대화상자와
  메뉴 조작을 자동화하지 못했다. 레지스트리 단위 검사와 웹뷰 E2E(취소·저장 안 함)로만 확인했다.
- 파일 > 열기·끌어다 놓기 실기: 네이티브 열기 대화상자와 실제 드래그는 조작하지 못했다. 열기는 파일 연결과 같은
  `deliver`(실기 확인)와 단위 검사, 끌어다 놓기는 E2E 의 합성 `DragEvent` 와 실기의 넘기기 경로(임시 패치)로 확인했다.
- 남은 경계: 시작 흐름 중에 열기를 취소하면 준비 보고까지 예약이 남아, 그사이 같은 파일을 다시 열면 그 창만 앞으로 온다.
  업데이트 적용은 저장하지 않은 창만 막으므로, 만드는 중이거나 여는 중인 문서는 재시작으로 닫힌다(편집 내용은 없다).
  다른 창이 연 파일 경로로 다른 이름으로 저장하면 두 창이 같은 경로를 갖는다(운영체제 덮어쓰기 확인만 있다). 만들어진 뒤
  웹뷰가 준비되기 전의 창으로 간 메뉴 명령은 사라진다.
- 실제 업데이트 경로에서 여러 창의 알림 1회·사전 차단: 이 변경을 포함한 버전을 설치한 다음 업데이트부터 확인할 수 있다.
